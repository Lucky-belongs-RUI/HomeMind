# Agent 离线评测（Eval）

回答一个问题：**改了 prompt、换了模型、调了规则之后，效果是变好还是变坏？**

没有评测时，所有"优化"都只是感觉；有评测时，每次改动都有可对比的数字。

---

## 快速开始

```bash
cd backend
pip install -r requirements-dev.txt

# 规则模式（离线、零 API Key、零成本，可在 CI 跑）
python -m evals.runner

# 只跑部分套件
python -m evals.runner --suite intent attribute

# 真实模型端到端（LangGraph 全图 + 真实 Qwen + 内存 SQLite，需配置模型 API Key）
python -m evals.e2e --json evals/reports/e2e.json

# HTTP 接口性能基准（ASGI 直连 + 内存 SQLite）
python -m evals.api_benchmark --json evals/reports/api.json

# 业务代码行覆盖率（标准库 sys.monitoring，无需 coverage 包）
python -m evals.coverage --json evals/reports/coverage.json
```

> conda 环境名为 `langGraph`（大写 G）。

## 标准工作流：改 prompt 前后对比

```bash
# 1. 改动前存档基线
python -m evals.runner --mode llm --json evals/reports/baseline.json

# 2. 修改 homemind/prompts.py，并提升 version

# 3. 跑同样的评测，与基线对比
python -m evals.runner --mode llm --baseline evals/reports/baseline.json
```

终端会输出每个套件的指标变化：

```
与基线对比（正数 = 变好）
--------------------------------------------------------------------
  意图分类     f1             84.6% → 88.5%  ↑ +3.9pt
  澄清决策     accuracy       85.0% → 80.0%  ↓ -5.0pt
--------------------------------------------------------------------
```

指标没有变差才合入；变差就回滚 prompt 的 version。

## 两种模式

| 模式 | 路径 | 依赖 | 用途 |
| --- | --- | --- | --- |
| `rule`（默认） | 规则引擎 | 无 | CI 门禁、回归验证、快速自检 |
| `llm` | 真实模型 + 生产 prompt | LLM API Key | 衡量 prompt 与模型的实际效果 |

`rule` 模式必须能离线跑通——这是评测体系能被持续使用的前提。
`llm` 模式只注入标准家庭上下文与生产 prompt，**不查数据库**，
因此它衡量的是 prompt + 模型的能力，不含 DB 层差异。

## 四个套件

| 套件 | 测什么 | 主指标 | 用例数 |
| --- | --- | --- | --- |
| `intent` | 意图分类（多标签） | micro-F1 / 完全匹配率 | 26 |
| `attribute` | 用户话术 → 设备参数抽取 | 字段准确率 | 22 |
| `clarification` | 是否在正确时机发起澄清 | 准确率 / FP / FN | 20 |
| `routing` | 激活哪几条执行链路 | micro-F1 | 14 |

### 为什么指标要分开看

- **意图分类**用 micro-F1 而不是 accuracy：一条输入可能同时激活多个意图，
  单标签 accuracy 会把"少识别一个意图"和"多识别一个意图"算成同样的错。
  同时给出**完全匹配率**——它最严格，衡量"整体理解对不对"。
- **澄清决策**区分 FP 与 FN，因为两类错误代价不同：
  - `FP`（该执行却去追问）→ 用户嫌啰嗦；
  - `FN`（该追问却直接执行）→ **可能把设备设成错误状态**，代价更高。
- **参数抽取**用字段级准确率 + 整例全中率：避免"只抽对一半字段却算全对"。

## 数据集设计原则

三个约定：

1. **可复现**：所有用例都在 `household.py` 定义的标准家庭下运行，
   与 `database/init.sql` 的演示数据一致，结果不受数据差异干扰；
2. **可回归**：修过的 bug 一律补成用例（如 `attr_002` 对应"热水器温度解析分支
   曾经不可达"、`intent_017` 对应"讲解类问题曾落入闲聊"）；
3. **可解释**：需要背景的用例带 `note` 字段，已知不符合理想行为的用例
   在 `note` 里写明限制（如 `route_014`）。

### 关于「当前基线是 100%」的说明（重要）

当前 82 条用例在规则模式下**全部通过**。这不是"系统很完美"，而是因为
**这份数据集的期望值是从现有规则引擎的行为反推出来的**——它的作用是
**行为基线（regression baseline）**：回答"这次改动有没有把已有行为改坏"，
而不是"现有行为是否正确"。

两者的区别很关键：

| 用途 | 能回答 | 不能回答 |
| --- | --- | --- |
| 行为基线（当前） | 改 prompt / 改规则后，行为是否偏离 | 偏离的方向是对是错 |
| 真值标注（目标） | 偏离的方向是对是错 | —— |

要升级为真正的 ground truth，需要**人工逐条评审期望值**：由业务方（而不是代码）
决定"把空调调到20度"到底该不该先追问房间。`note` 字段就是为这个评审过程准备的。

`llm` 模式的分数才有参考价值——因为那条路径的期望值是业务判断，而模型输出不受代码约束。

- `2`：缺少依赖

## 扩展方向

- **答案忠实度（faithfulness）**：知识问答链路目前只测路由，未测"回答是否忠于检索片段"，
  可引入 LLM-as-judge 打分；
- **澄清召回**：补充规则前置判断（如体感描述、作息暗示）降低 FN，同时保持 FP 为 0；
- **覆盖率口径**：接入分支覆盖率，并为 `agent/` 的模型调用节点补充桩数据单测。
