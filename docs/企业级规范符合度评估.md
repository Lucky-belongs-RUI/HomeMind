# 企业级 Agent 应用规范符合度评估

> 评估目标：判断本项目是否达到"企业级 AI/Agent 应用"的工程规范，并给出面向 **AI 岗位面试** 的改造优先级。
> 评估方式：全量静态阅读 `backend/app`（96 个 Python 模块）、`frontend/src`、根目录配置与文档，逐项取证。

---

## 一、总体结论

**架构能力已经达到企业水平，工程规范还停留在个人项目水平。**

这句话需要拆开说，因为它决定你的改造策略：

- **能体现"你会做 Agent"的部分，你做得比大多数面试项目好**：LangGraph 多链路并发编排、人在环审批（interrupt）、多模型抽象 + 规则降级、RAG 双集合隔离、Postgres checkpointer 持久化、家庭级三级权限矩阵。这些是稀缺的，面试时能讲 40 分钟。
- **能体现"你会做工程"的部分，几乎全部缺失**：0 个测试、0 个自定义异常、无 lint/类型检查、无 CI、无 `pyproject.toml`、51 个路由只有 1 个声明响应模型、47 处函数内 import 暴露循环依赖。

面试官通常分两轮看：一面看架构与 AI 理解（你稳过），二面/交叉面看工程素养（这里会被打穿）。**下面的改造，本质是补第二块。**

## 二、目录与分层设计

### 现状

采用**技术分层**（按技术类型分目录），这是国内企业 Python 项目最主流的方式，方向正确：

```
app/
├── api/        路由层（9 个模块）
├── services/   业务逻辑层（12 个模块）
├── models/     ORM（8 个）
├── schemas/    Pydantic（8 个）
├── agent/      graph / state / nodes / rules / tools / persistence / memory / studio
├── llm/        base / factory / 4 个 provider / dashscope_embedder
├── rag/        chunker / embedder / retriever / vector_store
├── voice/  websocket/  scheduler/
└── config.py  database.py  main.py
```

### 问题（按严重度）

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **顶层包名 `app`** | 企业项目用项目名（`homemind`）。`from app.xxx` 在多项目共存、打包发布、或与 Django 生态混用时会冲突；面试官看到 `app` 会默认是"跟着教程起的名字" |
| 2 | **`homemind/__init__.py` 缺失** | 实测只有子包有 `__init__.py`，顶层是隐式 namespace package。能跑，但打包（setuptools）、类型检查、IDE 索引都会出问题 |
| 3 | **`config.py` / `database.py` 裸露在顶层** | 基础设施代码应有归属，标准做法是 `core/`（或 `infra/`）。目前它们与业务模块平级，层级关系表达不出来 |
| 4 | **`agent/` 混装 5 类职责** | 编排（`graph.py`/`state.py`）、节点（`nodes/`）、规则（`rules/`）、工具（`tools/`）、运行时基础设施（`persistence.py`/`memory.py`/`studio.py`）。后三个明显不属于"Agent 编排" |
| 5 | **`schemas/` 名不副实** | 里面全是 `LoginRequest` / `AgentChatRequest` 这类**请求**模型，几乎没有响应模型。目录名叫 schemas，实际只是 request DTO |
| 6 | **`llm/` 职责越界** | `dashscope_embedder.py` 是 embedding，属于 RAG 的检索链路，不属于 LLM chat 抽象层；而 `rag/embedder.py` 只是一个转发壳，两层职责对调了 |
| 7 | **`services/` 后缀冗余** | 目录已表达 service 语义，文件名再带 `_service` 是重复（`services/device_service.py` → `services/device.py`） |
| 8 | **缺 4 个关键目录** | `tests/`（测试）、`prompts/`（提示词）、`core/`（基础设施）、`docs/`（文档）。其中 `tests/` 和 `prompts/` 对 AI 项目是刚需 |
| 9 | **`agent/nodes/_base.py`** | 下划线前缀在 Python 里表示"私有模块"，但它是被 13 个节点共用的公共模块，语义反了 |
| 10 | **根目录混入调试产物** | `_check_rules.py`、`_test_intent.py`、`_err6.png` 三个临时文件躺在仓库根目录（未被 git 跟踪，但存在于工作区）。同时三份大文档（107KB / 77KB / 23KB）也堆在根目录而非 `docs/` |
| 11 | **单文件过大** | `agent/rules/intent.py` 740 行、`agent/nodes/task_planning.py` 347 行。规则层应该按"规则集"拆目录 |

## 三、模块耦合与依赖方向（最刺眼的工程信号）

**全项目 47 处函数内 `import`。**

```
agent/tools/device_tools.py     10 处
api/agent.py                     6 处
services/file_service.py         4 处
main.py                          4 处
services/family_service.py       3 处
services/scene_service.py        3 处
agent/nodes/task_planning.py     3 处
agent/nodes/intent_recognition.py 3 处
...
```

函数内 import 的唯一正当理由是**打破循环依赖**。企业代码评审看到这个模式，第一反应就是"分层有环"。而实际情况更糟——**同一个 service 层内部就有环**：

```
services/scene_service.py  ──(函数内 import)──▶  services/device_service.py
services/room_service.py   ──(函数内 import)──▶  services/device_service.py
services/family_service.py ──(函数内 import)──▶  room_service / device_service / scene_service
```

`device_service` 是基础层，`room` / `scene` / `family` 都依赖它——但依赖方向没有被显式建模，只能靠延迟导入绕过。**这说明 service 层的职责边界是"按业务实体切"，而不是"按依赖层次切"。**

标准做法：

1. 明确单向依赖：`api → services → repositories → models`，`agent → services`（不允许反向）
2. 数据访问下沉到 `repositories/`，让 service 之间不再互相调用（`scene_service` 需要设备数据时，注入 repository 而不是 import 另一个 service）
3. 跨模块共享的东西下沉到 `core/`

面试时这一条很容易被追问："你这 47 处函数内 import 是为什么？" —— 目前没有好答案。

## 四、异常体系与响应契约

### 4.1 零自定义异常类

全项目 **没有任何 `class XxxError(Exception)`**。业务语义全部用 Python 内置异常表达：

```python
# services/auth_service.py
raise ValueError("用户名已存在")
raise PermissionError("只有房主可以创建子账户")

# services/device_service.py
raise ValueError(f"设备不存在: {device_id}")
raise PermissionError(f"设备不属于家庭 {family_id}，无权操作")
```

API 层再统一转译：

```python
except ValueError as exc:
    raise HTTPException(status_code=400, detail=str(exc))
```

这带来四个问题：

1. **语义丢失**：`ValueError` 本意是"值不合法"，用它表示"用户名已存在"（其实是冲突）或"设备不存在"（其实是 404）都是错的
2. **无法区分状态码**：所有业务错误被压成 400 或 404，靠开发者手工判断该用哪个
3. **没有错误码**：前端只能靠匹配中文文案做处理，无法国际化、无法精准分支
4. **内部信息泄露**：`str(exc)` 直接把内部错误文本透给客户端

企业标准做法：

```
core/exceptions.py
    class AppError(Exception):        # 基类，携带 code / message / http_status
    class NotFoundError(AppError)     # → 404
    class PermissionDeniedError(AppError)  # → 403
    class ConflictError(AppError)     # → 409
    class ValidationError(AppError)   # → 422

main.py
    @app.exception_handler(AppError)  # 全局统一转译 + 统一响应体
```

### 4.2 响应契约不一致

- **51 个路由，只有 1 个声明了 `response_model`**（`api/file.py` 的 `FileStatusResponse`）
- 返回格式混用：`{"success": True}` / 裸 `list` / 裸 `dict` / `{"file_id": ..., "status": ...}`
- 没有统一响应包装（企业常见 `{code, message, data}` 或 `{data, meta}`）
- 创建类接口没有用 `status_code=201`
- 列表接口没有分页规范（`GET /files` 直接返回全量 list，无 `limit`/`offset`）

后果：前端每个接口都要写不同的解析逻辑；接口文档（`/docs`）里响应结构全是空的 `{}`。

## 五、AI/Agent 项目特有规范（面试真正的分水岭）

普通 CRUD 项目的规范你补一补就齐了。但"AI 面试项目"的差异化在下面这张表——**这才是面试官用来区分"用过 LLM"和"做过 AI 工程"的地方**。

| 能力项 | 当前状态 | 企业要求 | 面试风险 |
| --- | --- | --- | --- |
| **评估体系（Eval）** | **完全空白** | 离线评测集 + 指标（意图准确率、工具调用成功率、答案忠实度）+ 回归门禁 | **极高**。面试官几乎必问"你怎么知道改了 prompt 之后变好了？" |
| **Prompt 管理** | 9 个常量散落在 8 个文件里（`INTENT_PROMPT`/`PLANNING_PROMPT`/`CHAT_PROMPT`…） | `prompts/` 集中 + 模板化 + 版本号 + 可灰度 | 高。"prompt 怎么版本管理 / A-B 测试？" |
| **可观测性** | 无 tracing。`langsmith` 已在依赖里但未接入 | LangSmith / Langfuse 逐步追踪，能回放一次失败会话 | 高。"线上一次会话失败，你怎么定位？" |
| **成本追踪** | `LLMResponse.usage` 拿到了直接丢弃 | token 计量落库，按用户/会话归因 | 中 |
| **工具注册机制** | `TOOL_DEFINITIONS` 列表 + `if/elif` 手工分发（`device_tools.py:137-150`） | Tool Registry + 装饰器注册 + schema 自动导出 | 中 |
| **结构化输出** | 手写 `extract_json` 正则截取 | Pydantic 校验 + 失败自动重试 | 中 |
| 多模型抽象 | ✅ 抽象基类 + 工厂 + contextvar 注入 | —— | 加分 |
| 降级策略 | ✅ LLM 失败自动回退规则引擎，且明确告知用户 | —— | 加分 |
| 状态机持久化 | ✅ Postgres checkpointer | —— | 加分 |
| 人在环（HITL） | ✅ `interrupt` 实现审批中断 | —— | 加分 |

**评估体系空白是最大的单点风险。** 它不只是"少个功能"——它会让面试官推断"这个人没有在生产环境迭代过 Agent"。因为只要真迭代过，第一件事就是建评测集。

## 七、代码风格与技术语言

### 做得规范的

- **PEP 8 命名**：`snake_case` 函数/变量、`PascalCase` 类、`UPPER_CASE` 常量，全项目一致
- **日志规范**：统一 `logger = logging.getLogger(__name__)`，无 `print`
- **docstring 质量高**：写的是"**为什么**这么做"而不是"这行代码做了什么"。例如 `state.py` 的 `_merge_avatar_emotion`、`api/deps.py` 的模块 docstring、`password_service.py` 解释为什么不用 passlib。**这一点比大多数面试项目强，是加分项**
- **分层抽象到位**：LLM 层有真正的抽象基类 + 工厂，不是 if/elif 堆砌

### 不一致的

- **类型注解风格混用**：`state.py` 用 `Dict[str, Any]` / `Optional[X]`，新代码用 `dict` / `X | None`。同一项目应统一（建议统一到现代写法）
- **中文 docstring 全覆盖**：国内面试完全 OK；但如果目标公司有开源文化或外企，需要英文
- **规则层硬编码过重**：`rules/intent.py` 740 行关键词分支，`if "感冒" in text` 这类硬编码遍布。面试官会问"这些规则怎么维护？和 LLM 的职责边界在哪？"

## 十一、改造记录（2026-10-16）

A 档六项已实施完毕，另追加一轮补齐。逐项对照：

| 项 | 状态 | 产出 |
| --- | --- | --- |
| ① 评估体系 | ✅ | `backend/evals/`：runner + metrics + household + 4 个数据集（82 例）+ README |
| ② 自动化测试 | ✅ | `backend/tests/`：8 个文件，全部零外部依赖 |
| ③ prompts 集中管理 | ✅ | `homemind/prompts/`：9 个 prompt 带 id/version，10 处调用点改造 |
| ④ 异常体系 | ✅ | `homemind/core/exceptions.py` + `handlers.py`，服务层与 API 层全量迁移 |
| ⑤ 代码质量工具 | ✅ | `ruff.toml` / `mypy.ini` / `pytest.ini`（**刻意不建 pyproject.toml**，原因见下） |
| ⑥ response_model + 清理 | ✅ | 50/51 路由补齐；`.dockerignore`；根目录调试产物已移出 |

### 关键结果

- **`response_model` 覆盖率 1/51 → 50/51**。唯一例外是 `POST /agent/tts`——它返回音频文件流，声明响应模型反而会破坏下载。
- **API 层 `HTTPException` 出现次数归零**：全部改为领域异常，错误响应统一带 `code` 字段（同时保留 `detail` 以兼容既有前端）。
- **服务层内置异常清零**：`raise ValueError/PermissionError` 只剩两处编程错误（未知 LLM provider、未知向量集合），属合理保留。

### 顺带修掉的两个缺陷

1. **`FileStatusResponse.chunk_count` 类型错误**：原声明为 `int = 0`，而文件处于 pending/processing/failed 时实际返回 `None`，响应校验会失败并返回 500。已改为 `Optional[int] = None`。
2. **家庭子资源接口泄漏内部字段**：`/families/{id}/rooms|devices|scenes` 原先直接返回 ORM 对象，把 `is_active`、`created_at` 等内部字段一并暴露，且与 `/rooms`、`/devices` 的形状不一致。已统一声明响应模型。**改动前已确认前端未调用这三个接口**，因此无破坏风险。

### 一个刻意的工程取舍：不建 pyproject.toml

`langgraph.json` 里的 `dependencies: ["."]` 会让 langgraph-cli 从本目录的依赖定义文件安装依赖。一旦出现 `pyproject.toml`，它就会改从 pyproject 安装——而本项目的依赖清单在 `requirements.txt`，两边打架会导致 `langgraph dev` 起不来。

因此工具配置改用 `ruff.toml` / `mypy.ini` / `pytest.ini` 三个独立文件。原因也写在 `ruff.toml` 顶部，便于后续维护者理解。

### 验证过程发现并修复的 3 个缺陷

**1. 参数抽取的正则贪婪匹配（真实生产 bug）**

`_parse_attributes` 里音量/频道的前缀用了 `.`：

```python
re.search(r"音量.{0,4}(\d{1,3})", "把音量调到20")   # 结果 volume = 0
```

`.` 是贪婪的，会先吃掉数字再回溯，最终只匹配到末位的 `0`。同一个 bug 也存在于电视的频道解析（`频道.{0,3}` 会把 `123` 解析成 `3`）。

修复：前缀改用 `[^\d]`，不允许吞掉数字。已补两条回归用例（`把音量调到20`、`电视调到频道123`）。

**2. `evals/runner.py` 数据集文件名映射错误**

套件名（`intent`）与数据集文件名（`intent_classification.yaml`）不一致，导致 `FileNotFoundError`。已补 `DATASET_FILES` 映射表并说明"套件名求短、文件名求自明"的取舍。

**3. `tests/test_prompts.py` 断言写错**

用 `assert "<" not in rendered` 判断占位符是否被替换——但替换进去的值本身含 `<`，断言恒假。已改为逐字段检查 `{name}` 是否残留。

### 两个值得记录的工程决策

**① LangSmith 配置必须写在 `config.py`，不能写在 lifespan**

`langgraph` / `langchain` 读取的是 `os.environ`，而 `.env` 只会被 pydantic-settings 解析进 `Settings` 对象、**不会**进入环境变量。且 langchain 可能在导入时就缓存追踪开关。

因此把 `_export_tracing_env()` 放在 `config.py` 模块底部——`config` 是几乎所有模块最先导入的模块，这是唯一可靠的时机。写在 lifespan 里会失效。

**② 评测基线 100% 不等于系统完美**

82 条用例全通过，是因为**期望值是从现有规则引擎行为反推的**。它的定位是**行为基线**（回答"改动有没有把行为改坏"），不是"真值标注"（回答"行为对不对"）。已在 `evals/README.md` 里用对照表说明这两者的区别，并指出升级路径是人工逐条评审期望值。

`llm` 模式的分数才有独立参考价值——那条路径的期望值不受代码约束。

## 十三、C-12 / C-13 实施记录（2026-10-16 第三轮）

### C-12：函数内 import 从 49 处降到 9 处

**核心发现：这些函数内 import 的根因不是循环依赖。**

我在第一份评估文档里写过"service 层内部就有环"，**这个判断是错的**。逐一验证依赖方向后确认：

```
agent.tools  → services.*        （services 不反向依赖 agent）✓ 单向
family_service → room/device/scene_service  ✓ 单向
room_service  → device_service              ✓ 单向
scene_service → device_service              ✓ 单向
```

**真正的两个根因是：**

1. **`rag/vector_store.py` 的模块级单例**
   ```python
   vector_store = VectorStore()   # 导入即创建 Chroma PersistentClient（文件锁 + 磁盘 IO）
   ```
   任何模块只要顶层导入它就会初始化向量库。这迫使 `file_service`、`knowledge_tool`
   全部改成函数内导入来规避副作用——**一个模块级副作用污染了整个项目的导入风格**。
   已改为 `get_vector_store()` 懒加载。

2. **防御性写法**：其余大多数是"怕出问题就先延迟导入"的历史习惯，并非真实约束。

**结果：49 → 9。剩余 9 处全部是刻意延迟：**

| 位置 | 数量 | 为什么保留 |
| --- | --- | --- |
| `agent/__init__.py` | 2 | `__getattr__` 实现惰性加载，这是模块设计本身 |
| `main.py` | 4 | 组合根：lifespan 内导入，避免在追踪初始化前加载重模块 |
| `scheduler/engine.py` | 1 | APScheduler 未安装时要能降级 |
| `core/exceptions.py` / `prompts/base.py` | 2 | docstring 里的示例代码（静态检查误报） |

**实际用于规避循环依赖的函数内导入：0 处。**
