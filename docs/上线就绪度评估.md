# 上线就绪度评估

> 视角：不是"代码有没有 bug"，而是"这套系统能不能真正对外运营"。
> 覆盖安全、可靠性、性能、合规、可观测性、部署、成本、业务完整性八个维度。
> 结论按 **阻断项（上线前必须解决）→ 上线后迭代项** 分级。

---

## 一、总体结论

**功能完成度很高，生产化程度很低。** 这两件事经常被混为一谈，但它们需要的投入完全不同。

已经做得扎实的部分（不重复造轮子）：

- **权限与隔离模型完整**：51 个 REST 路由全部挂了鉴权依赖，房主/住户/访客三级权限在路由层、服务层、工具层都有落地；`family_id` 一路透传到 SQL 查询条件；私人文件 vs 家庭规章制度的可见性规则清晰（`file_service.list_files`）。
- **数据库设计规范**：`database/init.sql` 有完整外键约束、复合索引（`idx_family_user_session`、`idx_family_type`）、`ON DELETE CASCADE`，不是随手建的库。
- **仓库卫生良好**：`.gitignore` 覆盖 `.env*`（保留 `*.env.example`）、`uploads/`、`chroma_data/`、`node_modules/`；实测 `backend/.env` **未被 git 跟踪**，`plugins/`、`node_modules/` 也未入库，175 个跟踪文件干净。
- **已具备部分生产意识**：`parse_file` 用 `asyncio.to_thread` 避免阻塞事件循环；STT 临时文件在 `finally` 里清理；前端有 401 自动登出、WebSocket 有重连。

缺的是**安全基线、运维能力、合规资质、成本控制**这四块——它们不体现在功能演示里，但每一条都会在上线后变成事故或账单。

## 二、安全（问题最集中，多项是硬红线）

### S1　密码明文存储 —— 上线红线

`auth_service.py` 的 `hash_password` / `verify_password` 直接返回/比对明文，docstring 写明"演示平台按需求明文保存密码，不做哈希与安全校验"。

**后果**：数据库一旦泄露（或运维误操作导出），所有用户密码直接暴露。用户普遍跨站复用密码，影响会外溢到其他系统。

**改法**：换 `bcrypt` 或 `argon2`（注意 bcrypt 有 72 字节上限，建议先做 sha256 预哈希或直接用 argon2）。存量演示数据建议直接重置，不要做兼容双读——双读逻辑会长期留在代码里成为隐患。

### S2　登录/注册无限流，可暴力破解与批量刷号

`/auth/login` 无失败计数、无验证码、无限速；`/auth/register` 同样无任何限制。

**后果**：密码明文 + 无限流 = 可离线爆破；`/register` 可脚本批量创建家庭，而每次注册后用户都能立刻消耗 LLM 与 embedding 额度——**这是直接的资损入口**。

**改法**：per-IP + per-account 失败计数与锁定、注册加验证码或邀请码、全局与 per-user 的请求限速。

### S3　JWT 无法吊销，且角色被写死在 token 里

`create_jwt_token` 把 `user_id / username / role / family_id` 全部写进 payload，有效期 24 小时（`config.py:69`）。

**后果**：房主把某住户踢出家庭或降级后，**该用户的旧 token 在 24 小时内依然能控制设备**——因为服务端只验签名，不回查 DB。同样，"退出登录"只是前端删 localStorage，服务端 token 仍然可用。

**改法**：两条路，选一条——(a) 引入 refresh token + access token 短时效（15 分钟）+ 服务端吊销名单；(b) 更简单：token 里只放 `user_id`，`role` / `family_id` 每次请求从 DB 取（配合缓存）。当前数据规模下 (b) 的代价更低且立刻消除问题。

### S4　`jwt_secret` 有硬编码默认值

`config.py:67`：`jwt_secret: str = "smart-home-secret-key-change-in-production"`。

**后果**：运维忘记配置时，服务照常启动，而密钥是公开的 —— 任何人都能伪造任意用户（包括房主）的 token。这类"默认值兜底"在演示阶段是便利，在生产是**静默的致命漏洞**。

**改法**：改为启动时校验，未配置即抛错退出。同理适用于 `postgres_url` 的默认口令。

### S5　上传文件的大小校验发生在读完内存之后

`api/file.py` 的顺序是：`content = await file.read()`（全量读进内存）→ 再判断 `len(content) > settings.max_file_size`。

**后果**：`max_file_size` 只挡住了"落盘"，没挡住"读内存"。攻击者发一个 2GB 的 body，进程会先尝试分配 2GB 内存 → 多 worker 下直接 OOM。这是典型的低成本 DoS。

**改法**：先校验 `Content-Length` 头；再改流式分块读取，累计超限立即中断并返回 413。

### S6　CORS 白名单写死 localhost

`main.py:59-69` 的 `allow_origins` 只有 `localhost:5173 / 127.0.0.1:5173 / localhost:8000`，且 `allow_credentials=True`。

**后果**：生产前端域名不在白名单，跨域请求全部被浏览器拦截。而最省事的"修复"往往是把 origins 改成 `["*"]` —— 在 `allow_credentials=True` 下这是危险组合（虽然 Starlette 会在这种情况下不回显凭据，但依赖框架行为兜底不是好设计）。

**改法**：`allow_origins` 走环境变量配置。

### S7　JWT 存 localStorage

`stores/user.js` 把 token 写进 `localStorage`。

**后果**：任意 XSS 即可窃取长期 token。这个项目的 XSS 面比一般后台大——有用户上传的文档名回显、有 LLM 生成的自由文本渲染、有用户昵称展示。

**改法**：优先 httpOnly + Secure Cookie（需配套 CSRF 防护）；若因跨域架构暂时保留 localStorage，至少补 CSP 并对所有用户可控文本做转义。

### S8　WebSocket 鉴权走 URL query

`useWebSocket.js:85` 把 token 拼在 `?token=`，`api/agent.py` 从 query 解析。token 会进入 Nginx access log、浏览器历史、Referer。

**改法**：改为连接后首帧鉴权消息，或用 `Sec-WebSocket-Protocol` 传递。同时把"鉴权失败不关闭连接"改成主动 `close(code=1008)`。

## 三、可靠性与数据一致性

### R1　每次启动都清空并全量重建向量库 —— 上线后最痛的一条

`main.py` 的 lifespan 调用 `file_service.rebuild_file_vectors()`，其内部逻辑是：`vector_store.clear_all()` → 遍历 `uploaded_files` 全部记录 → 逐文件重新解析 + 重新调用 DashScope embedding。

**后果**（四条同时成立）：

1. **每次发布/重启都是一次事故窗口**：期间知识问答链路完全不可用（向量库被清空）。
2. **启动时间随文件量线性增长**，文件上百后可能几分钟起不来。
3. **中途失败即残缺**：没有事务、没有回滚，向量库停在半成品状态。
4. **每次重启都重复烧钱**：全量重算 embedding，这是按量计费的 API。

**改法**：改为幂等增量索引 —— 启动时只做"对账"（DB 有记录但向量库没有的才补），维度迁移作为一次性的、显式触发的运维动作，而不是每次启动的固定流程。

### R2　文件处理是 fire-and-forget 任务

`api/file.py:70`：`asyncio.create_task(file_service.process_file_async(record.id, collection))`。

四个问题叠在一起：

1. **返回的 Task 没有保存引用** —— Python 官方文档明确警告：未引用的 Task 可能在执行完成前被垃圾回收。
2. **没有队列**：进程重启/崩溃，任务直接丢失，文件永远卡在 `processing` 状态，前端一直转圈。
3. **没有并发上限**：同时上传多个大文件会打爆内存与 DashScope 限流。
4. **多副本下任务只在单个进程内**。

**改法**：换成持久化任务队列（短期可用"DB job 表 + APScheduler 轮询"，不必立刻上 Celery/ARQ），并在启动时把遗留的 `processing` 记录重置为 `pending` 重新入队。

### R3　无数据库迁移工具

`ensure_collection_column()` 在启动时执行 `ALTER TABLE` 来兼容旧库。

**后果**：多副本并发启动会有 DDL 竞争；结构变更无法回滚；变更历史无记录。

**改法**：引入 Alembic。这是有存量数据后的必然选择，越早引入成本越低。

### R4　无优雅停机

lifespan 会 `stop_scheduler` 与 `shutdown_persistence`，但 uvicorn 没有配置 graceful shutdown 等待窗口。

**后果**：滚动发布时，正在执行的 Agent 请求会被直接切断。**注意副作用已经产生**——设备控制可能执行到一半（比如场景里 4 个动作执行了 2 个），用户却看到连接断开。

**改法**：配置 `--timeout-graceful-shutdown`，并让 uvicorn 等待进行中的请求结束。

### R5　四处状态、零备份策略

MySQL（业务数据）、Postgres（LangGraph checkpoint + store）、Chroma/JSON（向量库）、`uploads/`（原始文件）——四处独立状态，没有任何备份约定或恢复演练。

向量库可以重建，但 `conversations`（对话历史）、`user_preferences`（用户画像）、`device_operation_logs`（操作审计）**丢了就没了**。

## 四、性能与容量

### P1　LLM 客户端没有超时控制

所有 LLM client 构造 `AsyncOpenAI` 时都没传 `timeout`，走 SDK 默认值（**600 秒超时 + 2 次自动重试**）。

**后果**：上游一次抖动，用户要等最长 10 分钟；期间该请求一直占着连接与 worker 槽位。交互式对话场景下这是不可接受的。

**改法**：显式设 `timeout=15~30s`，并配合 `max_retries` 与退避策略。这一条同时能缓解 R4（长请求更难被优雅停机等待）。

### P2　前端 HTTP 超时 30s，可能短于后端真实耗时

`api/request.js:10` 设了 `timeout: 30000`。而 `POST /api/agent/chat` 内部要串行调用 2~4 次 LLM（意图识别 → 任务规划 → 回复生成）。

**后果**：慢模型或网络抖动时前端先超时，用户看到"请求失败"，**但服务端其实已经执行完设备控制了**。用户以为没生效会再点一次 → 重复执行。这是典型的"前端以为失败、后端已经成功"的不一致。

**改法**：Agent 对话强制走 WebSocket（已有实现）；或把 HTTP 超时提到 60s+，并在 UI 上明确区分"请求超时（结果未知）"与"执行失败"。

### P3　无并发与配额限制

没有 per-user 的 QPS 上限，也没有日调用量上限。

**后果**：单个用户（或一段脚本）可以无限消耗 LLM + embedding 额度。叠加 S2 的无限注册，等于把计费账号暴露给公网。

**改法**：per-user 日调用上限 + 全局并发上限 + 超额降级到规则回复。

### P4　WebSocket 是单机内存态

`ws_manager.active_connections` 是进程内字典。

**后果**：多副本部署时，A 副本上的设备变更广播不到连在 B 副本的同家庭用户。设备状态推送会随机失效。

**改法**：Redis pub/sub 广播，或负载均衡层做会话粘性（但粘性无法解决跨副本广播的根本问题）。

### P5　单 worker 部署

`Dockerfile` 的 `CMD` 没有 `--workers`。async IO 是并发的，但 CPU 密集操作仍会阻塞事件循环——`parse_file` 已用 `to_thread` 处理，但 `vector_store` 的本地 JSON 回退路径（`_query_local` 的余弦相似度是纯 Python 循环）是同步的，向量一多会明显卡住。

这一节在功能演示阶段完全不会暴露，但它决定"能不能合法上线"，不是"要不要做"的问题。

## 六、可观测性

### O1　没有任何日志配置

全项目没有 `logging.basicConfig` / `dictConfig`。日志级别、格式、输出目标（stdout JSON / 文件轮转）都未定义。

更麻烦的是 `log_node_run` 会把**整个节点的返回值**打进日志——里面包含用户对话内容与完整设备状态。这既是日志量成本，也是隐私问题（日志通常保留更久、权限更松）。

**改法**：统一日志配置；节点日志改为只记关键字段 + 耗时；敏感字段脱敏。

### O2　没有链路追踪

没有 trace_id / request_id。一次 Agent 请求会产生十几条互不关联的日志（意图识别、全屋状态、各链路节点、工具执行…）。线上排障基本靠猜时间戳。

### O3　没有指标

没有 Prometheus 或任何 metrics 暴露。无法回答最基本的问题：今天的失败率、P95 延迟、token 花了多少钱。而 `LLMResponse.usage`（prompt_tokens / completion_tokens）已经拿到了，只是被直接丢弃。

### O4　健康检查过于简单

只有 `GET /` 返回一个静态 JSON，不校验 MySQL / Postgres / 向量库连通性。

**后果**：K8s 用它做 liveness/readiness 时，一个"进程活着但数据库连不上"的实例会继续留在负载均衡里接流量，然后每个请求都失败。

**改法**：拆成 `/healthz`（进程存活，不查依赖）与 `/readyz`（校验关键依赖连通性）。

### O5　无错误上报

没有 Sentry 之类的异常聚合。生产异常只进日志，没有人会主动去看。

| D1 | **无 CI/CD** | 没有 `.github/workflows`，没有 lint / 类型检查 / 测试门禁。配合"项目无 tests/"的现状，等于没有任何回归防线 |

## 八、成本控制

- **无 token 计量与配额**（同 P3）——无法归因"哪个用户花了多少钱"
- **每次重启全量重算 embedding**（同 R1）——最直接的浪费
- **无 LLM 结果缓存**——相同意图反复调用
- **无模型降级链路**——贵模型失败不会自动切便宜的，直接落到规则回复

---

## 九、缺失的业务能力（用户上手就会撞到）

- **忘记密码 / 密码重置**：现在只有"改密码"，且必须先知道旧密码。用户忘记密码 = 账号永久丢失
- **账号注销**：合规要求，也是基本产品能力
- **多端登录管理 / 强制下线**：与 S3 同源
- **操作审计查询**：`device_operation_logs` 表一直在写数据，但没有对应 API，数据只进不出
- **设备/房间/场景批量导入**：目前只能一个个建

## 十二、一句话总结

**这套系统目前是"一个做得很好的体验平台"，还不是"一个可以对外运营的产品"。** 差距不在业务逻辑——Agent 编排、权限隔离、数据模型都够用；差距在它从来没有被当作一个会被人攻击、会被发布重启、会被监管、会烧钱的生产系统来对待。第十节的 11 项里，前 5 项是安全红线（不做就是等着出事），第 6–10 项是运维底线（不做就是每次发布都提心吊胆），第 11 项是合法性的前提。这 11 项做完，它就从"能演示"变成了"能上线"。

### 数据兼容性

无需手工迁移：演示账号（`owner01` 等）的明文密码会在首次成功登录时自动升级为 bcrypt 哈希。上线前建议直接删除全部演示账号，或登录一次完成升级后立即改密。

### 本轮未处理，需要你决策

**`family_service.create_family_with_owner` 的硬编码默认密码。** 该函数给新建家庭的房主账号写死密码 `123456`（`family_service.py:71`，`api/family.py:34` 的 docstring 与代码一致），且该密码不会返回给调用者。

风险：任何知道这个固定值的人，都能登录由该接口创建出来的房主账号——而这些账号拥有对应家庭的完整控制权。

修复需要前端增加"设置新家庭密码"的输入项（或改为生成随机密码并在响应中返回、由前端展示一次），属于 API 契约变更，故未擅自改动，等你确认交互方式后再改。
